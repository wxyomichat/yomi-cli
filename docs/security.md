# 安全说明

`yomi` 处理三类敏感信息：登录时网页交来的一次性授权码（120 秒内有效、只能换取一次，绑定本次登录的 `state`、端口和 PKCE challenge）和只留在 CLI 内存里的 PKCE `code_verifier`、CLI 自己的会话（`auth_token` / `refresh_token`），以及会花钱的操作（付费预演消息）。过渡期内旧版授权页仍可能交来 Firebase ID token（见 3 和「已知风险」）。下面逐项说明 CLI 怎样处理它们，以及还没解决的风险。协议细节见 [auth-protocol.md](auth-protocol.md)。

## 1. 只接受本机回环回调

- 回调服务只绑定 `127.0.0.1`，端口随机（系统分配），不监听 `0.0.0.0`。
- 对端地址必须是回环地址；`Host` 头必须是 `127.0.0.1:<port>` 或 `localhost:<port>`，防 DNS rebinding（恶意网页把自己的域名解析到 127.0.0.1 后访问回调）。
- `Origin` 必须等于所选环境的网页 origin。其他网站的页面即使知道端口，也无法让浏览器带着 Yomi 的 `Origin` 提交；`Origin: null`（沙箱 iframe、data URL）同样拒绝。授权页提交前把 referrer 策略设为 `origin`，否则 https → http 的提交会被浏览器改成 `Origin: null`。因 `Origin`、`state`、内容格式或授权码格式不符被拒绝的回调，会在终端里提示原因（不含凭证，前三次逐条提示），等待继续；`Host`、路径或方法不符的请求直接拒绝，不在终端提示。
- 无效回调再多也不会结束等待：如果几个错误请求就能让 CLI 停止监听，别人就能占住空出来的端口，接住用户随后点「授权」时发出的授权码。（没有 `code_verifier`，接住的授权码也换不出会话；v1 的 token 则不然。）
- 网页端只按校验过的 `port` 拼 `http://127.0.0.1:<port>/callback`，主机和路径写死，不能被参数改成别的地址，不会变成开放重定向。

## 2. state 每次登录一个

- `state` 为 32 字节密码学随机数，每次 `yomi login` 重新生成，只存在内存里。同一次登录里，回答被拒绝后同一个 `state` 仍然有效；登录结束（确认、取消或超时）后作废。
- 回调用常数时间比较。`state` 有 256 位，猜不出来，所以错误的 `state` 只拒绝、不计数。登录结束后回调随即关闭、CLI 退出：关闭前片刻到达的请求得到 410，之后连接直接被拒。
- 终端与网页同时显示由 `state` 派生的确认码，用户核对一致才点授权，防止钓鱼页面诱导用户授权别人发起的登录。
- 换出会话时先在一个不碰本机凭证的会话里试用，再在终端显示**服务端返回**的账号（名字、user_id 和 App 里可见的 UID；服务端给了邮箱时也显示，只有 v1 兜底会给）。名字由账号主人自己设置，可以冒充；用 UID（或 user_id）核对是不是自己的账号；交互运行时要输入 `y` 确认才保存，`n` 拒绝（其他输入会再问一次；提问前敲的输入会被丢弃，在终端里连没按回车的字符也一并丢弃，不会被当成回答）。「交互运行」指标准输入和输出都是终端；把输出接到管道（如 `yomi login | tee log`）就是非交互运行。网页表单里的邮箱和名字不采用。拒绝时撤销刚建立的会话，回调继续用同一个 `state` 等待。
- 网页上的「取消」同样先交给终端：交互运行时问一句是否结束登录，不是你点的就输入 `n` 继续等待。
- 所以本机另一个用户即使从进程参数里读到了授权链接（Linux 上 `xdg-open` 的参数别人可以看到），在交互运行时抢先用自己账号的授权码（他可以拿链接里的 challenge 为自己的账号申请一枚）、v1 的 token 或一个伪造的「取消」回调，也既不能让 CLI 登录到他的账号，也不能让 CLI 停止监听、腾出端口。非交互运行时没人可问，第一个有效回答直接生效，登录随即结束、端口空出（见「已知风险」）。

## 3. 授权码与 PKCE；凭证不进 URL，也不进日志

- 网页不再交出 Firebase token 或网页会话，而是用自己的会话申请一枚一次性授权码交给 CLI。授权码 120 秒内有效，服务端第一次读到就作废（不论成败），并且绑定本次登录的 `state`、回调端口和 `code_challenge`。
- PKCE（RFC 7636，S256）：每次 `yomi login` 生成 32 字节随机的 `code_verifier`，只留在 CLI 进程的内存里，不打印、不写日志、不落盘、不进错误信息；链接里只有它的 SHA-256（`code_challenge`）。授权码在回传途中即使被本机别的程序截走，没有 verifier 也换不出会话。
- 授权码只出现在表单 POST 正文里；带查询串的回调请求一律拒绝。
- 授权页链接只带 `port`、`state`（不是凭证，只防 CSRF）、`code_challenge`（公开值）和展示用的字段，而且放在 URL 片段 `#…` 里：片段不发给服务器，不进访问日志和 Referer；网页读出后立即从地址栏删掉，RUM 上报也会去掉它。
- CLI 拿到授权码后只调用一次 `account/exchange_cli_auth_code`，从不重发（同一次登录里再收到用过的码，不发请求直接拒绝）；网络出错时码可能已经被用掉，登录随即结束，提示重新运行 `yomi login`。之后只用 CLI 自己的会话。
- 过渡期：旧版授权页仍交来 Firebase ID token 时，CLI 照旧只调用一次 `account/login`，不保存、不打印，并提示网页还是旧版。
- `--debug` 的请求日志只打印方法、路径、状态码和耗时，不打印请求体；所有调试输出和错误信息经过 `redact()`，去掉 `token`、`auth_token`、`refresh_token`、`firebase_token`、`id_token`、`code_verifier`、`X-Token`、`state`，以及 JSON 或表单里的 `code`（数字状态码不受影响）。
- 长连接按服务端协议要求把 `refresh_token` 放在 `wss://…/connection/ws?token=…` 里（与 App、网页一致）。这个地址只在内存里交给 WebSocket，从不打印；走 TLS，也不经过浏览器历史。这是服务端协议本身的限制，见「已知风险」。

## 4. 凭证保存

- 默认存系统钥匙串：macOS 用 `security`（服务名 `yomi-cli`，账户为环境名 `test` / `prod`），Linux 用 Secret Service（`secret-tool`）。写入时密钥经标准输入传给 `security -i`（十六进制 `-X`）或 `secret-tool store`，不出现在命令行参数里，`ps` 看不到。
- 没有钥匙串时退到 `~/.config/yomi-cli/credentials.json`：目录 0700、文件 0600，先写临时文件再原子改名。会给出提示。`YOMI_CREDENTIAL_STORE=file` 可强制使用文件（测试、无桌面环境）。
- 本地状态文件（`state/*.json`，请求回执、草稿编号、上传记录）不含任何凭证。
- `yomi logout` 先调用 `account/logout` 撤销服务端会话，再删除本机凭证；服务端失败时仍删除本机副本并提示。如果登出时会话需要先刷新，撤销的是刷新后的 `refresh_token`，不是已经被换掉的旧值。
- 重新 `login` 时，新会话先存好，再撤销被替换的旧 CLI 会话（存的时候持有刷新锁，同时读出被替换的那一对，所以别的 `yomi` 进程刚刷新过也能撤销对）；新会话存不进去（钥匙串锁住、磁盘写不了）时，撤销新会话，旧的登录保持不变。
- 登录过程中建立、但最终没有用上的会话（被拒绝、读回失败、按了 Ctrl+C）都会撤销。换取会话的请求（v1 为 `account/login`）发出后不会被 Ctrl+C 打断，等它返回再撤销它建立的会话；否则服务端建了会话，CLI 却拿不到，无法撤销。换取请求在网络上失败时，服务端可能已经建了会话而 CLI 不知道，这个会话只能等它过期。
- 服务端按（账号，设备）记 CLI 的会话：同一台机器、同一个账号再次登录时，服务端在换取这一刻就替换旧的 CLI 会话。所以这时在终端回答 `n`，旧会话也已经回不来了，需要再登录一次；同一账号经授权码再次登录时，CLI 撤销被替换的会话发现服务端已经结束了它，不会误报撤销失败；换了账号或经 v1 兜底登录时，撤销被拒绝可能是令牌已被别的进程刷新，仍会提示。
- 撤销是尽力而为：网络出错，或令牌已被别的进程刷新时，撤销可能失败，会话会留在服务端直到过期。被替换的旧会话、存储失败时的新会话、`yomi logout` 撤销失败时，终端都会提示；处理办法见 5.1。按两次 Ctrl+C 强行退出时，正在建立或正在撤销的会话也可能留下。

## 5. CLI 会话与 App、网页隔离

- CLI 用授权码换出**自己的**会话（独立 `device_id`），不复用网页的 `refresh_token`，所以 CLI 刷新令牌不会让网页掉线，撤销 CLI 会话也不影响网页和 App；换取会话也不会让任何一端下线。
- 服务端把这个会话记为 CLI 自己的会话，与网页、App 分开：在网页或 App 上重新登录不会让它失效。`yomi logout`、刷新令牌过期、注销账号仍会让它失效。
- 例外是过渡期的 v1 兜底：旧版授权页交来 Firebase token 时，CLI 用 `account/login`（带 `not_logout_other_device: true`）以网页平台的身份登录，而网页登录时会让同平台的其他会话失效，所以在任何浏览器里重新登录 Yomi 网页，这样的 CLI 会话会掉线，需要再 `yomi login`。终端在这种登录时会提示。
- 刷新令牌失败（过期、被撤销）时 CLI 删除本机凭证，要求重新登录；多个 CLI 进程同时运行时，若钥匙串里已有别的进程刷新过的新令牌，直接采用，不重复刷新。

## 5.1 电脑丢失或凭证外泄时

- 还能用这台电脑：运行 `yomi logout`，撤销服务端会话并删除本机凭证。如果它提示服务端注销没有成功，或者说本机没有登录，本机的令牌可能已经被别人刷新换掉，服务端的会话仍然有效：再按下一条处理。
- 用不了这台电脑：目前没有「已登录设备」列表可以单独踢掉 CLI。用授权码登录的 CLI 会话不受网页重新登录影响，只能等服务端让长期不用的会话过期（或注销账号）。过渡期内经旧版授权页（v1）登录的 CLI 会话属于网页平台：在任意浏览器重新登录一次 Yomi 网页即可让它失效，代价是其他浏览器也要重新登录。
- 用过 `yomi relay` 的话，bot 的凭证（Telegram 的 bot token、QQ 的 AppSecret、微信 ClawBot 的登录凭证）也保存在这台电脑上（系统钥匙串，或 `--allow-file-store` 时的 0600 文件），和 CLI 会话一起暴露，`yomi logout` 不会删除它们。不论还能不能用这台电脑，都到发放凭证的地方让它失效：
  - Telegram：在 @BotFather 里对这个 bot 发 `/revoke`，让旧 token 失效（之后用新 token 运行 `yomi relay --telegram --set-token` 并重新配对）；
  - QQ：在 QQ 开放平台（q.qq.com）这个机器人的「开发设置 → APPID 接入凭证」里重置 AppSecret（之后 `yomi relay --channel qq --set-app`），见 [relay-qq.md](relay-qq.md)；
  - 微信：在手机微信里解除 ClawBot 的绑定，见 [relay-wechat.md](relay-wechat.md)。

  还能用这台电脑时，先停掉正在运行的 relay，再运行 `yomi relay --forget --all`，删除本机所有 bot 的凭证、配对信息、花费记录和后台服务（只删一个：`yomi relay --forget --bot <名字>`）。

- 服务端提供设备列表和按设备撤销之后，CLI 会跟进。

## 6. 超时与取消

- 授权默认 300 秒有效（`--timeout` 可改，最长 3600），超时后回调服务关闭，`state` 作废。收到有效回答（授权码、token 或取消）后，从换会话、读回账号到终端确认（交互运行时）这段时间不计时；继续等待时只计算剩下的时间，所以实际等待可能比 `--timeout` 长（每个服务端请求最长约 20 秒）。
- 凭证保存之前，Ctrl+C 在任何一步（包括确认提问处）都取消这次登录：关闭回调服务，已经建立的会话撤销后才退出，不保存。正在进行的换取请求（v1 为 `account/login`）会等它返回。再按一次立即退出（这时正在建立的会话可能留下）。
- 凭证保存之后（正在撤销被替换的旧会话时）按 Ctrl+C 不会撤回这次登录，只会提示；再按一次立即退出，旧会话可能没有撤销。
- 网页上点「取消」会告诉 CLI：非交互运行时登录结束；交互运行时终端会问一句，确认后结束。终端正在确认时，网页上的「取消」得到 409（页面提示到终端处理），这时在终端回答或按 Ctrl+C。

## 7. 花钱与生产环境

- 默认连生产环境，这也是唯一内置的环境；测试环境要显式 `--env test` 并自己配置地址，用 `YOMI_API_ORIGIN` / `YOMI_WEB_ORIGIN` 指向的 mock 或本地构建不算生产。生产环境的 `create` / `preview` / `relay` 需要再输入 `prod` 确认（非交互时需 `--confirm-prod`）。
- 预演开始先显示服务端返回的剩余免费条数。用完后，CLI 先查询并显示钻石余额，用户输入 `yes` 才会以 `consumption_mode=1`（付费）发送；非交互运行必须加 `--allow-paid`，否则停止。CLI 从不在未确认的情况下发付费消息。
- 18+ 与版权声明每次 `create` / `preview` 都要确认（输入 `yes`，或非交互时显式 `--accept-declaration`），不写在角色文件里。
- 同一个 Yomi 账号和环境，本机同时只运行一个 relay，不论通道（Telegram 也一样，由本机锁文件保证）：否则几个 relay 会共用 Yomi 长连接的设备 ID、抢走彼此的离线消息，各自一份的 `--max-spend` 本机上限可以被花上几遍，按余额差额核对的花费也会互相算错。

## 已知风险与后续

1. **授权码经过浏览器**：授权码是一次性的、120 秒内有效，并且用 PKCE 与发起登录的 CLI 绑定，截走它的人没有 `code_verifier` 换不出会话。仍然存在的是 v1 兜底：过渡期内旧版授权页交来的 Firebase ID token 在 1 小时内可以换出会话，也没有与 CLI 绑定。缓解：只发给本机回环、表单 POST、不进 URL；无效回调不会让 CLI 腾出端口；终端确认服务端返回的账号。网页的 v2 普及后，CLI 会移除这个兜底。
2. **本机其他进程**：同一用户下的恶意进程理论上可以抢先监听或读取钥匙串，这超出 CLI 能防御的范围（`gh`、`gcloud` 同样如此）。本机另一个用户如果读到授权链接（`state` 和 `code_challenge`）：他可以为**自己的**账号申请授权码抢先回调，交互运行时这和伪造的「取消」都要经过终端确认，拒绝即可；非交互运行时没人可问，他的授权码会直接让 CLI 登录到他的账号，伪造的「取消」会结束登录。这两种情况登录都随即结束、端口空出：之后你在网页上点「授权」得到的授权码即使被抢占端口的人接走，没有 verifier 也换不出你的会话（旧版授权页交出的 token 则可以在 1 小时内被利用）。所以非交互运行时终端会提醒：没在网页上点过授权就不要再点，账号不是你的就 `yomi logout`。需要防这种情况时，请直接在终端里运行 `yomi login`。
3. **长连接 URL 中的 refresh_token**：服务端协议所致；若服务端支持握手后鉴权或短期连接票据，CLI 可以跟进。
4. **Safari**：从 https 页面向 `http://127.0.0.1` 提交表单，个别 Safari 版本可能提示「此表单不安全」。用户确认后仍可提交；也可以用 `--no-browser` 把地址复制到 Chrome。
5. **用授权码登录的 CLI 会话无法从别处单独结束**：它不再随网页重新登录失效（这是有意的），而目前也没有设备列表可以单独撤销它。电脑丢失时只能等它过期或注销账号（见 5.1）；服务端提供设备列表后 CLI 会跟进。
